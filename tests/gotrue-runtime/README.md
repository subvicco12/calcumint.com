# Genuine local GoTrue acceptance

Run `node tests/gotrue-runtime/acceptance.mjs` from the repository root with installed locked dependencies, Chromium and the managed local Docker socket available. Preload the three digest-pinned images declared in `fixture.mjs`; the harness uses `--pull=never`. `GOTRUE_ARTIFACTS` may name an evidence directory (created recursively if absent); by default evidence goes to a fresh temporary directory. Generated credentials/tokens are never written to evidence.

This suite runs actual GoTrue v2.197.0, PostgreSQL 17.6, PostgREST 12.2.3, installed Supabase JS/SSR dependencies and the actual Next development server/browser login actions. Native Chromium edits/submits the application's login form; no synthetic provider, user/session table, injected browser session or cookie is used. Existing synthetic suites remain separately scoped.

GoTrue source: https://github.com/supabase/auth/tree/v2.197.0 (release target commit `4eee58f296d9698a1c2c0ae14d7a0b379c7622d3`). Docker image digest `sha256:1736a63078f5922b198c4cbe50f80ab9a2d3b54fe8b7b6cfb2e9dc5dbbc12c6b`. Image and source retrieval used the configured proxy with TLS verification. Supabase changelog retrieval was denied by configured network policy; this does not block local upstream source/image acceptance.

The dedicated non-superuser `supabase_auth_admin` owns the empty auth schema before GoTrue automatically applies its 75 bundled upstream migrations. Those migrations create the real users, identities, refresh tokens, sessions and auth helpers. In particular `00_init_auth_schema.up.sql` creates `auth.uid()`, and `20220224000811_update_auth_functions.up.sql` supplies the JWT claims-aware implementation. The suite asserts its actual owner/body; no modeled auth helper is installed.

`schema.mjs` lists/hashes the selective, unchanged app migrations 001/002/009/010/029 and declares fixture ACLs explicitly. This is account/history acceptance, not a full migration-chain or hosted-platform parity claim. No guarded proposals are applied. Production equivalence remains UNKNOWN. A transparent loopback gateway adapts `/auth/v1` and `/rest/v1` routing and CORS only, forwarding upstream response status/body. All containers share a disposable internal Docker network with no published ports; DB storage is tmpfs. Generated local-only JWT secrets and credentials are discarded with cleanup.

Email autoconfirm is enabled solely for this local fixture. SMTP delivery, email confirmation, recovery, OAuth, remote credentials, production infrastructure, payments, certification and publication are outside acceptance. No production build runs. Actual browser proof covers sign-in, SSR-cookie reload persistence and sign-out. The existing signup UI's email-confirmation notice is not accepted as evidence of mail delivery.

Assertions cover trigger-created Free profile/preferences; untrusted metadata cannot elevate signed role/plan; bad-password and wrong-signature rejection; authentic owner/outsider history RLS; rejected foreign-owner/plan writes; authenticated-user denial of auth-admin APIs; rejection of anon/service JWTs without user subject at `/user`; rotated refresh tokens; live auth.sessions membership followed by deletion and refresh rejection after logout. A valid service-role JWT intentionally remains privileged for PostgREST: the suite does not assert otherwise. PostgREST accepts the still-valid access JWT immediately after logout; this immediate behavior is measured explicitly. The elapsed expiry boundary is NOT tested. This is not represented as immediate access-token revocation. Browser page errors and attempted requests outside the two allowed local origins fail acceptance.
