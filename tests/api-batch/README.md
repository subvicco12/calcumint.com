# Durable batch request contract (unapplied proposal)

Baseline: draft #1443 (`0a7d9af97da42ab01a18f5ec7aa0bad0015a4474`). Run `node tests/api-batch/atomic-postgres.mjs`; pinned PostgreSQL runs on a temporary internal Docker network, no host ports or production configuration. Actual migrations 005/006 provide delivery, usage and job tables over explicit synthetic organization/auth/builder prerequisites. Guards are stripped only from fixture stdin.

The client UUID is a correlation token, not an authoritative job identity. Server verification resolves API-key hash, key and organization; SQL rechecks active key/scope/Business authority, serializes on the key, binds the original calculator/inputs, generates the job UUID, and pins published version plus exact definition before new persistence. The receipt binds key+request UUID to immutable job identity/input/output. Canonical JSONB comparisons accept JSON object-key ordering differences; numeric JSON overflow is rejected before submission to avoid Infinity-to-null loss.

POST missing probe is read-only. Successful new POST and accepted duplicate POST each consume **one request unit**, never one unit per row. Duplicate POST returns the original job/version without recalculating or rewriting its result. An exhausted duplicate POST returns 429; authenticated same-key GET recovery retrieves the committed historical job without an additional debit. GET does not execute an unpublished calculator. Revoked keys, removed scopes and non-Business owners cannot recover data.

Policy adoption remains required: unlike legacy authentication's pre-debit, rejected validation/probes and an uncommitted job leave no debit. This is necessary for the proposed quota+job rollback contract but is not an inferred owner-approved billing policy. Rejected/probe traffic needs separately reviewed abuse controls. No automatic write retry is performed after uncertain outcome; caller retains the same key and uses GET. Missing recovery does not prove that an in-flight transaction can never commit.

**Dependencies:** all writers must use the key-lock quota contract, including the separate guarded ATOMIC-API-QUOTA.sql proposal. READ COMMITTED is enforced; stronger snapshot modes fail closed. Existing session/role quota timezone is preserved. Receipt serialization omits timezone-formatted audit timestamps. Test scenarios cover simultaneous duplicates and conflicts, independent minute/month boundaries, mixed legacy/new writers, ownership/hash/scope/Business, stale version/definition, corrupt row acknowledgements, job/receipt/usage rollback, recovery at exhausted quota, role denial, timezone-independent evidence and receipt/job corruption. Application tests cover no REST fallback, stable request IDs, acknowledgement correlation, ordered outputs and unmetered verification without leaking key hashes to ordinary principals.

Not established: production schema/ACL/owner/default-role fidelity; external writers; immutable builder-definition enforcement outside this function; deletion/retention and receipt PII policy; full deployed gateway transport or performance. SQL trusts server-generated deterministic outputs and is service-role-only; it does not independently run TypeScript formulas or validate the raw API secret. Existing jobs without receipts are not retroactively declared idempotent.

Guarded SQL lives outside migrations and is never applied to production by this task. Adoption must review function ownership/EXECUTE, existing RLS, actual migration history, retention and joint route/RPC rollout. No production atomicity or exactly-once network claim.
