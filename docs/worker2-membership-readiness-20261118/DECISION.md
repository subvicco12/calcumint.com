## Exact dependencies and scope

- [Standalone fencing](../architecture/proposals/MEMBERSHIP-ADMIN-FENCING.sql), SHA-256 `441e03f864004c5abfadf6f0840e18938e793c9ce7b73c3af766d51bbfebb912`. It is guarded and transactional. It depends on migration 003's membership and organization tables and policies, the role helpers after migration 013's RPC privilege changes, and the reviewed [helper proposal](../architecture/proposals/API-RLS-HELPER-EXECUTE.sql), SHA-256 `11d26ff8339e614256fa2faab4c2c6f243ef1cdeec6d080d1ef08ff87f5c5ccf`.
- Intended authenticated EXECUTE is limited to the caller-constrained membership predicates `is_org_member` and `has_org_role`. `org_role` is internal. All three helpers in 003 are stable definers whose lookup uses `auth.uid()`. The standalone preflight checks effective authenticated EXECUTE for only two functions and the existence of one policy. It does not bind function bodies, ownership, search paths, policy expressions, inherited grants for other roles, or table and column grants.
- The [composite account proposal](../architecture/proposals/20261021-v1-authentic-account-security.sql), SHA-256 `a4075c12645710adf1bada346c85d1115984b88760318a7ec63a6d05a4ed2bc7`, explicitly removes direct grants to `org_role` before its prerequisites. The separately reviewed [atomic privileges proposal](../architecture/proposals/20261021-v1-atomic-object-privileges.sql) also revokes `service_role` EXECUTE on the trigger functions. The standalone file revokes PUBLIC, anon and authenticated there. Do not infer the effective hosted ACL of a replaced function from the standalone SQL.
- Review coexistence with [Owner P0 membership](../owner-p0/membership.md) before choosing an artifact. That separate held successor fences owner demotion/removal and owner ID writes, serializes membership/invitation writers, applies capacity rules and rejects service-role membership writes. Standalone fencing preserves owner transfer primitives and has no atomic ownership transfer. Neither artifact is interchangeable.

## Contract findings

| Boundary | Evidence and remaining gap |
|---|---|

The proposal is not a complete actor/target transition matrix, Business-plan gate, or audited administration API. |

Define the acceptance boundary explicitly and test writer ordering for the chosen successor. |
| Audit and account recovery | Existing organization bootstrap and invitation acceptance write audit records. The standalone proposal adds no same-transaction audit for direct role edits or revocations, and does not change personal history/scenario ownership. Admin UI must retain immutable personal recovery and must not silently change shared snapshot ownership. |
| Fail closed | The new disposable probe submits only unchanged guarded files and confirms unchanged policy, trigger and helper ACL metadata. ## Minimal UI design for separate approval

Show manage controls only in the selected Business organization after a fresh entitlement and membership read. Start owner-only for non-owner targets unless the owner approves a broader actor/target matrix. Offer explicit role choices, a separate revoke confirmation, and refresh the roster and project access on success or on stale state. Keep a readable error, keyboard focus, and a recoverable stale-state path. Keep ownership transfer out of scope.

The mutation boundary should derive the actor from a verified session, bind tenant and target to the current roster, recheck role and entitlement in the write transaction, and compare an expected prior state. Choose deterministic lock ordering with the accepted membership/invitation writer contract. Record actor, organization, target, old/new role or revoke and a stable request ID in the same transaction. Authorize direct API calls by the same rules and account for any remaining table writers. Deny/no-op outcomes must not create success audit records. Do not use a browser-controlled role or an unrestricted service role as authority.
